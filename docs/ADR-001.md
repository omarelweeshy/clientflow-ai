# ADR 001: Business state stays in FastAPI and PostgreSQL

Accepted: 2026-10-09. The repository was empty.

Use Next.js for the same-origin UI and API proxy, FastAPI for all business decisions, SQLAlchemy/Alembic with PostgreSQL for persistent state, and n8n for polling and integration orchestration. SQLite is used only for fast isolated tests and a fallback developer preview. PostgreSQL is the Docker default.

Intake persists before extraction. Demo mode processes immediately so it works without n8n. Set ORCHESTRATION_MODE=n8n to leave ingestion pending for the intake workflow. Both paths call the same idempotent business operation. n8n never owns approval, delivery eligibility, scoring or follow-up state.

The default adapters are deterministic extraction, internal CRM and a persistent mock email outbox. Ollama, HubSpot contact synchronization, SMTP and Slack are optional. HubSpot mirrors contacts; opportunities stay in the internal CRM. SMTP has no provider idempotency guarantee, so an ambiguous delivery is blocked for reconciliation rather than blindly resent.

Initial email and each follow-up require separate approval. The dashboard's explicit safe-automation option may bypass approval only for complete, high-category, consented initial responses. It is disabled by default; follow-ups always need approval.

Single-organization administration uses an environment-configured password hash, signed HTTP-only session cookie and session-bound CSRF token. Public intake is separate. Automation uses a separate shared secret, never the administrator cookie. PostgreSQL row locks serialize processing and delivery. Database constraints provide durable deduplication. Exact duplicate matching uses normalized email plus enquiry fingerprint; an email with a different enquiry creates a new opportunity and is flagged as a probable duplicate.
